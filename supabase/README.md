# Supabase Schema Notes

## Slice 1 Foundation

- `auth.users` is the source of truth for identities.
- `firm_members.user_id` references `auth.users(id)` directly and stores firm-local profile fields such as `full_name`.
- Every tenant-owned table has `firm_id` from Slice 1 onward.
- `audit_events` is append-only. The migration installs `audit_events_prevent_update` and `audit_events_prevent_delete` triggers, both of which raise for every role before mutation.
- `firms.retention_days` defaults to 2555 days and is documented against Money Laundering Regulations 2017, regulation 40.
- Slice 4 portal work is intentionally deferred and will live in `apps/portal/`, not inside `apps/web/`, because it has a separate magic-link auth model and can run on a separate domain.

## Slice 0b: permissions in the database

- `public.require_role(firm_id, roles[])` is called at the top of every write RPC that used to check only active membership. `read_only` can no longer write; `review_entity_cdd` needs `admin` or `reviewer` (`reviewer` is not an assignable role yet).
- `entity_cdd_records.fetched_by` is set by `save_entity_cdd`; `firms.four_eyes` (default true) stops the fetcher approving their own record.
- `supabase/tests/permissions.test.sql` checks all of this inside one transaction that is rolled back. Run it against a database that has the migrations applied:

  ```
  psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -c "begin" -f supabase/tests/permissions.test.sql -c "rollback"
  ```
- Saving a filing is maker-checker: `register_document` stores it with status `pending`; an admin approves it with `approve_filing_document`, and with `firms.four_eyes` on, not the person who saved it (`client_documents.uploaded_by`).
- `supabase/tests/permissions.dryrun.sql` (generated by `node supabase/tests/build-dryrun.cjs`) wraps the migration and the tests in one transaction that rolls back, for pasting into the dashboard SQL editor.

### Dry-running the Slice 0b migration (`scripts/run-dryrun.cjs`)

The Supabase dashboard SQL editor does not reliably run a script as one transaction, so it is not a
supported way to dry-run this migration. Use the script, which runs everything over a single
connection and always rolls back:

```
DRYRUN_DB_URL='postgresql://...' node scripts/run-dryrun.cjs
```

(or `npm run dryrun:slice0b` with the variable set). Use a database that does **not** already have the
migration, such as a Supabase branch or a local stack: for a hosted project, take the direct (port 5432)
or session-pooler connection string from the dashboard, with `?sslmode=require`; the transaction-mode
pooler (port 6543) is not suitable.

What it does:

1. Prints whether the migration is already applied (`require_role`, `firms.four_eyes`,
   `entity_cdd_records.fetched_by`). If it is, it stops without running anything.
2. `BEGIN`, then `supabase/migrations/20261014000000_slice0b_permissions.sql` and
   `supabase/tests/permissions.test.sql` (read from disk, one statement at a time), printing each
   `NOTICE` (`PASS: ...`, then `ALL PERMISSION TESTS PASSED`) as it arrives.
3. `ROLLBACK` in a `finally`, even on error. On an error it prints the message, code, position and the
   file and line it maps to.
4. Prints the same check again to show nothing persisted.

Exit code 0 means the tests passed and the post-rollback check is clean (2: already applied, 3: could not
connect, 1: a test failed, 4: something persisted). The connection string is never printed; host, user,
password and database name are scrubbed from any error text.

The splitter it uses has its own tests: `npm run test:scripts`. `permissions.dryrun.sql` (from
`node supabase/tests/build-dryrun.cjs`) is still generated for use with `psql`, but is not needed by the script.
